Redis 지연 문제를 공부하면서 가장 인상 깊었던 건, 트래픽이 아니라 명령어 하나가 전체를 멈출 수 있다는 점이었습니다.

## 싱글 스레드라는 전제

Redis의 명령 처리는 기본적으로 싱글 스레드입니다. 어떤 명령이 오래 걸리면 그 뒤의 모든 명령이 줄을 서서 기다립니다. 여기에 수백만 필드짜리 해시 같은 빅키가 있으면 문제가 됩니다. `HGETALL`, `SMEMBERS`, `KEYS`, 큰 키에 대한 `DEL` 같은 O(N) 명령이 이벤트 루프를 수백 ms씩 점유하면, 평소 1ms 미만이던 p99가 수백 ms로 튑니다.

## 대응 세 가지

**1. 빅키를 만들지 않기 — 키 샤딩.** 하나의 거대한 해시 대신 suffix로 쪼갭니다.

```
user:sessions          (필드 500만 개)   ← 위험
user:sessions:{0..99}  (필드 5만 개씩)   ← 안전
```

**2. 전체 조회 대신 분할 순회.** `HGETALL` 대신 `HSCAN`으로 커서 기반 분할 조회를 하면 한 번에 잡는 시간이 짧아집니다.

```
HSCAN user:sessions:3 0 COUNT 1000
```

**3. 삭제는 DEL 대신 UNLINK.** `DEL`은 메모리 해제를 동기로 수행해 빅키에서 오래 걸리지만, `UNLINK`는 키를 즉시 분리하고 실제 해제는 백그라운드 스레드가 처리합니다.

`SLOWLOG GET`과 `redis-cli --bigkeys`로 현재 상태를 진단하는 것부터 시작하면 됩니다.

## 정리

- Redis 지연의 단골 원인은 트래픽이 아니라 "한 방이 큰 명령"이다.
- 빅키는 설계 단계에서 샤딩으로 예방하는 게 최선.
- 운영 중이라면 HSCAN 분할 + UNLINK 전환만으로도 p99가 크게 안정된다.
