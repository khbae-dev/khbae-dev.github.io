운영 중인 DB에 대량 마이그레이션을 돌리는 게 왜 위험한지 구조적으로 정리해 봤습니다. 단순히 "부하가 커서"가 아니라 연쇄 반응이 문제였습니다.

## 장애로 번지는 연쇄 구조

1. 대량 배치 UPDATE/INSERT가 WAL과 임시 파일을 쏟아내며 디스크를 잠식한다.
2. 디스크 I/O가 느려지면서 트랜잭션 하나하나가 길어진다.
3. 길어진 트랜잭션이 락을 오래 붙잡는다.
4. 그 락을 기다리는 쿼리가 줄을 서고, 락 큐 뒤의 모든 쿼리가 함께 멈춘다.

즉 마이그레이션 자체가 아니라, 마이그레이션이 만든 긴 트랜잭션과 락 대기 행렬이 서비스를 멈추게 합니다.

## 안전하게 돌리는 세 가지 장치

**1. 저부하 구간에 작은 배치로 나눠 돌리기.** 한 방 쿼리 대신 PK 범위로 쪼개서 커밋을 자주 합니다.

```sql
-- 예: 10만 건씩 나눠서 처리
UPDATE orders SET status_v2 = mapped(status)
WHERE id BETWEEN :start AND :start + 100000;
COMMIT;
```

**2. lock_timeout을 짧게.** 락을 못 잡으면 빠르게 실패시켜 락 큐가 쌓이는 것을 막습니다. 실패한 배치는 재시도하면 됩니다.

```sql
SET lock_timeout = '3s';
```

**3. 구조 변경이 큰 경우 논리 복제 cutover.** 새 스키마의 테이블(또는 인스턴스)로 논리 복제를 걸어 데이터를 따라잡게 한 뒤, 짧은 순간에 쓰기 대상만 전환합니다. 애플리케이션 입장에서는 수 초 수준의 전환만 체감됩니다.

## 정리

- 마이그레이션 장애의 본질은 부하가 아니라 락 큐다.
- 배치 분할 + 짧은 lock_timeout만으로도 "전체 멈춤"은 대부분 예방된다.
- 대규모 스키마 전환은 논리 복제로 병행 준비 후 cutover가 정석이다.
