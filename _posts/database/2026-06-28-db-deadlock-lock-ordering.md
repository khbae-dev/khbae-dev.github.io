`Deadlock found when trying to get lock` 에러를 만나면 반사적으로 재시도 로직부터 늘리기 쉽습니다. 그런데 공부해 보니 순서가 반대였습니다. 데드락은 대부분 구조적으로 없앨 수 있고, 재시도는 그 다음 보완재였습니다.

## 데드락이 생기는 구조

전형적인 패턴은 두 트랜잭션이 같은 행들을 반대 순서로 잠그는 경우입니다.

```
Tx A: id=1 잠금 → id=2 잠금 시도(대기)
Tx B: id=2 잠금 → id=1 잠금 시도(대기)
→ 서로가 서로를 기다리는 순환 대기 = 데드락
```

계좌 이체처럼 "보내는 쪽과 받는 쪽을 함께 갱신"하는 로직에서 자주 나옵니다.

## 해결: 락 획득 순서 통일

모든 트랜잭션이 행을 같은 순서(예: PK 오름차순)로 잠그면 순환 대기 자체가 성립하지 않습니다.

```sql
-- 나쁨: 비즈니스 순서대로 잠금 (from → to)
UPDATE accounts SET balance = balance - 100 WHERE id = :from;
UPDATE accounts SET balance = balance + 100 WHERE id = :to;

-- 좋음: 항상 id 오름차순으로 잠근 뒤 갱신
SELECT * FROM accounts
WHERE id IN (:from, :to)
ORDER BY id
FOR UPDATE;
```

애플리케이션 코드라면 잠글 대상 id 목록을 정렬한 뒤 순서대로 처리하는 규칙을 팀 컨벤션으로 못 박는 게 핵심입니다.

## 재시도는 마지막 흡수 장치

순서를 통일해도 갭 락 등으로 드물게 데드락이 날 수 있습니다. 이건 짧은 백오프를 둔 재시도로 흡수합니다. 다만 재시도가 "주 대책"이 되는 순간 데드락 빈도가 늘 때마다 지연과 부하가 함께 늘어나므로, 어디까지나 보조 수단입니다.

## 정리

- 데드락의 원인은 운이 아니라 락 순서의 비일관성이다.
- 잠금 순서를 PK 오름차순으로 통일하면 순환 대기가 구조적으로 사라진다.
- 남는 잔여 케이스만 백오프 재시도로 흡수한다.
