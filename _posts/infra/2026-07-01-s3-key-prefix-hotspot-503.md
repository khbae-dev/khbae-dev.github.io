S3는 무한히 확장된다고 알고 있었는데, 503 SlowDown을 만나는 경우가 있다는 걸 공부했습니다. 총량이 아니라 "쏠림"의 문제였습니다.

## 파티션은 prefix로 나뉜다

S3는 내부적으로 key 이름의 앞부분(prefix)을 기준으로 파티션을 나눠 부하를 분산합니다. 파티션당 처리량 기준선은 초당 PUT/POST/DELETE 약 3,500, GET 약 5,500 요청입니다. 대부분의 워크로드엔 충분하지만, key 설계가 이렇다면 얘기가 달라집니다.

```
logs/2026-07-01/00-01-23-abc.json
logs/2026-07-01/00-01-24-def.json
logs/2026-07-01/00-01-25-ghi.json
```

모든 쓰기가 `logs/2026-07-01/` prefix에 집중됩니다. S3가 파티션을 자동 분할하긴 하지만 분할이 따라잡기 전까지 해당 파티션이 포화되고, 503 SlowDown이 돌아옵니다. 날짜·순번 기반 key가 흔해서 자주 밟는 지뢰입니다.

## 해시 prefix로 강제 분산

key 앞머리에 무작위성(해시 몇 자리)을 넣으면 파티션이 자연스럽게 여러 개로 나뉩니다.

```
# before: 단일 prefix에 집중
logs/2026-07-01/00-01-23-abc.json

# after: 해시 4자리를 앞에 → 최대 65,536개 prefix로 분산
a3f2/logs/2026-07-01/00-01-23-abc.json
7c19/logs/2026-07-01/00-01-24-def.json
```

해시는 파일명이나 ID의 md5 앞 몇 자리면 충분합니다. 대신 날짜 기반 목록 조회(ListObjects)가 어려워지므로, 목록이 필요하면 인벤토리나 별도 인덱스(DynamoDB)로 보완합니다. Athena/Glue 파티셔닝과의 호환도 설계 때 함께 고려해야 합니다.

재시도도 함께 챙깁니다. 503은 일시적 신호라 지수 백오프 재시도(SDK 기본 제공)로 흡수하되, 근본은 key 설계입니다.

## 정리

- S3 성능 한도는 버킷이 아니라 prefix(파티션) 단위로 걸린다.
- 시간·순번 기반 key는 쓰기 핫스팟의 전형이다.
- 해시 prefix 분산이 정석, 대신 목록 조회 전략을 함께 설계한다.
