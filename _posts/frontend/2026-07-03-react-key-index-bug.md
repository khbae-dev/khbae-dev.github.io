리액트에서 리스트를 정렬했는데 입력값이 엉뚱한 행에 남아 있는 버그를 공부했습니다. 원인은 딱 한 줄, `key={index}`였습니다.

## key는 "누구인지"를 알려주는 신분증

리액트는 리렌더 때 이전 트리와 새 트리를 비교(reconciliation)하면서, 리스트 항목은 key로 동일성을 판단합니다. key가 같으면 "같은 항목"으로 보고 기존 DOM과 컴포넌트 상태를 재사용합니다.

key를 인덱스로 주면 문제가 생깁니다. 정렬로 항목 순서가 바뀌어도 인덱스 0, 1, 2…는 그대로이기 때문에, 리액트 입장에선 "항목은 그대로인데 내용만 바뀌었다"로 해석합니다. 그래서 uncontrolled input 값, 체크 상태, 내부 useState 같은 것들이 원래 자리(인덱스)에 남고, 데이터만 다른 항목 것으로 교체됩니다. 상태가 다른 행에 "빙의"하는 겁니다.

```jsx
// 나쁨: 정렬·삭제·중간 삽입에서 상태가 꼬인다
{items.map((item, i) => <Row key={i} item={item} />)}

// 좋음: 데이터의 고유 id가 신분증
{items.map((item) => <Row key={item.id} item={item} />)}
```

## 인덱스 key가 허용되는 좁은 예외

리스트가 정적이고(추가·삭제·정렬 없음), 항목에 상태가 없고, id로 쓸 값이 정말 없을 때 정도입니다. 반대로 `Math.random()`을 key로 쓰는 건 최악입니다. 매 렌더마다 전부 "새 항목"으로 취급돼 DOM을 통째로 다시 만듭니다.

서버 데이터에 id가 없다면 생성 시점에 클라이언트에서 `crypto.randomUUID()`로 한 번 부여해 데이터에 저장해 두면 됩니다. 렌더 중 생성이 아니라 "데이터에 박아두는" 게 포인트입니다.

## 정리

- key는 성능 힌트가 아니라 정체성 선언이다. 잘못되면 상태 버그로 돌아온다.
- 순서가 바뀔 수 있는 리스트에서 key={index}는 잠재 버그다.
- key는 항목의 생애 동안 불변인 고유 값(id)으로, 렌더 밖에서 정한다.
