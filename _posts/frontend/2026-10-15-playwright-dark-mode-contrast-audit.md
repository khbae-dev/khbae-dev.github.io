기존 웹 앱에 다크 모드 스킨을 덧입히는 작업을 했습니다. 기본 화면은 금방 맞췄는데, 버튼을 눌러야 뜨는 모달, 드롭다운, 날짜 선택기 같은 곳에서 "흰 카드 위 흰 글자"가 계속 나왔습니다. 화면 수십 개를 사람이 매번 눌러 볼 수는 없어서 점검을 자동화했습니다.

## 1. 정해진 시나리오 대신 "누를 수 있는 것은 다 누른다"

화면마다 시나리오를 손으로 적으면 적지 않은 곳은 영영 안 봅니다. 그래서 탐색기 방식으로 바꿨습니다.

1. 화면에서 누를 수 있는 후보(버튼, 탭, 드롭다운, 날짜 입력 등)를 모은다.
2. 로그아웃, 저장, 삭제, 새로고침처럼 **상태를 바꾸는 버튼은 이름으로 건너뛴다.**
3. 하나씩 누르고, 새로 뜬 겹침 요소(모달, 드로어, 팝오버, 드롭다운)를 찾아 찍고 잰다.
4. 닫는다. 안 닫히거나 화면이 바뀌었으면 화면을 다시 열고 다음 후보로 간다.
5. 같은 종류·같은 제목의 겹침 요소는 한 번만 기록한다.

목록이 비어 있으면 "행을 눌러 여는 상세 모달"은 영영 안 열립니다. 그래서 가짜 백엔드에 표본 행을 넣어 두었습니다.

## 2. 글자 대비는 "실제로 보이는 배경" 기준으로

`getComputedStyle(el).backgroundColor`만 보면 대부분 `transparent`입니다. 실제 배경은 부모를 타고 올라가며 반투명 색이 겹친 결과입니다. 그래서 불투명한 배경을 만날 때까지 올라간 뒤, 위에서부터 알파 블렌딩으로 합쳤습니다.

```js
const parse = (c) => { const m = c?.match(/rgba?\(([^)]+)\)/); if (!m) return null;
  const [r, g, b, a = 1] = m[1].split(',').map(parseFloat); return { r, g, b, a }; };

const blend = (top, under) => ({
  r: top.r * top.a + under.r * (1 - top.a),
  g: top.g * top.a + under.g * (1 - top.a),
  b: top.b * top.a + under.b * (1 - top.a), a: 1 });

function effectiveBackground(el, pageBase) {
  const stack = [];
  for (let n = el; n && n.nodeType === 1; n = n.parentElement) {
    const c = parse(getComputedStyle(n).backgroundColor);
    if (c && c.a > 0) { stack.push(c); if (c.a >= 0.99) break; }
  }
  return stack.reverse().reduce((base, c) => blend(c, base), pageBase);
}
```

대비는 WCAG 공식 그대로입니다. 기준은 일반 글자 4.5:1, 큰 글자 3:1입니다.

```js
const lum = ({ r, g, b }) => {
  const f = (v) => { v /= 255; return v <= 0.03928 ? v / 12.92 : ((v + 0.055) / 1.055) ** 2.4; };
  return 0.2126 * f(r) + 0.7152 * f(g) + 0.0722 * f(b);
};
const contrast = (a, b) => { const [hi, lo] = [lum(a), lum(b)].sort((x, y) => y - x); return (hi + 0.05) / (lo + 0.05); };
```

## 3. "다크인데 밝은 상자"도 찾는다

대비가 충분해도 다크 화면 한가운데 흰 카드가 있으면 스킨이 닿지 않은 자리입니다. 화면에서 일정 크기 이상이고 불투명한 상자의 휘도를 재서, 다크 모드인데 밝거나(휘도 0.6 초과) 라이트 모드인데 어두운(0.04 미만) 것을 표시했습니다.

이때 **클래스 사슬**을 같이 남긴 것이 가장 쓸모 있었습니다.

```text
light-box-in-dark  #ffffff  640x320
div.page > div.ant-card > div.ant-card-body > form.ant-form
```

어떤 선택자를 덮어써야 하는지가 바로 보입니다. 덮어쓸 대상이 서드파티 컴포넌트의 4단계 선택자였다면, 내 다크 스킨 선택자의 우선순위가 그보다 높아야 한다는 것도 여기서 알 수 있었습니다.

## 4. 결과물

- 라이트와 다크 각각 화면별 스크린샷, 그리고 열어 본 겹침 요소마다 한 장씩
- 컴포넌트 종류별(버튼, 입력칸, 표 머리, 모달 등) 실제 배경색·글자색·대비 요약
- 기준 미달 목록과 클래스 사슬

이 도구로 찾은 것 중에는 대비만으로는 안 보이는 것도 있었습니다. 다크 스타일시트가 웹 폰트 이름만 걸고 `@font-face` 선언은 일부 앱에만 있어서, 그 앱의 영문과 숫자가 브라우저 기본 세리프로 떨어지고 있었습니다. 스크린샷을 나란히 보니 바로 보였습니다.

## 정리

- 다크 모드 결함은 눌러야 뜨는 곳에 숨어 있다. 시나리오 대신 탐색 방식으로 겹침 요소까지 열어 본다.
- 대비는 투명 배경을 부모까지 블렌딩한 실제 배경으로 계산한다.
- 결함마다 클래스 사슬을 남기면 고칠 선택자를 바로 정할 수 있다.
- 상태를 바꾸는 버튼은 이름으로 건너뛰고, 빈 목록에는 표본 데이터를 넣어 상세 화면까지 닿게 한다.
