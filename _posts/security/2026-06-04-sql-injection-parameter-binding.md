가장 오래됐지만 여전히 상위권인 취약점, SQL 인젝션을 기본부터 정리했습니다. 방어법이 이렇게 단순한데도 사고가 계속 나는 게 흥미로운 지점입니다.

## 값과 코드가 섞이는 게 문제

사용자 입력을 쿼리 문자열에 그대로 이어붙이면, 입력이 데이터가 아니라 SQL 문법으로 해석될 수 있습니다.

```javascript
// 취약: 입력을 문자열로 연결
const q = `SELECT * FROM users WHERE email = '${email}'`;
```

공격자가 email에 `' OR '1'='1`을 넣으면 쿼리가 이렇게 됩니다.

```sql
SELECT * FROM users WHERE email = '' OR '1'='1'
-- WHERE 조건이 항상 참 → 전체 테이블 반환
```

`'; DROP TABLE users; --` 같은 입력이면 파괴적 명령까지 실행됩니다. 로그인 우회, 데이터 덤프, 테이블 삭제가 전부 이 한 가지 원리에서 나옵니다.

## 파라미터 바인딩: 값은 언제나 값으로

해결은 값과 쿼리 구조를 처음부터 분리해서 보내는 겁니다. 플레이스홀더를 쓰고 값은 별도로 넘기면, DB 드라이버가 값을 항상 "데이터"로만 취급합니다.

```javascript
// 안전: 파라미터 바인딩 (prepared statement)
const q = "SELECT * FROM users WHERE email = $1";
const rows = await db.query(q, [email]);
// email에 무슨 문자가 있든 SQL 문법이 아니라 문자열 값으로만 처리
```

이제 `' OR '1'='1`을 넣어도, 그저 "그런 이메일을 가진 사용자"를 찾을 뿐 문법으로 해석되지 않습니다. ORM을 쓰면 대부분 자동으로 바인딩되지만, raw 쿼리나 문자열 연결을 섞는 순간 구멍이 생기므로 주의합니다. 방어를 겹치려면 최소 권한 DB 계정(애플리케이션 계정에 DROP 권한 제거), 입력 검증, WAF를 더합니다. 다만 근본이자 충분조건은 파라미터 바인딩입니다.

## 정리

- SQL 인젝션의 원인은 값과 코드가 문자열에서 섞이는 것 하나다.
- 파라미터 바인딩(prepared statement)이 근본이자 사실상 완전한 해결책이다.
- ORM도 raw 문자열 연결을 섞으면 뚫린다. "절대 문자열로 안 잇는다"를 규칙으로.
