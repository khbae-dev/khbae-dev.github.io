JWT 인증의 대표 취약점 두 가지를 공부했습니다. 공통 원인은 하나입니다. 검증 로직이 "토큰이 스스로 밝힌 알고리즘"을 믿는다는 것.

## 공격자가 검증 방식을 고르게 되는 문제

JWT 헤더에는 서명 알고리즘을 나타내는 `alg` 필드가 있습니다. 검증 코드가 이 값을 그대로 따르면, 공격자가 `alg`를 조작해 검증을 무력화할 수 있습니다.

**alg=none.** `alg`를 `none`으로 바꾸고 서명 부분을 비우면, "서명 검증 불필요"로 해석하는 구현에서 아무 토큰이나 통과합니다. payload를 마음대로 고쳐 관리자로 위장할 수 있습니다.

**RS256 → HS256 혼동.** 서버가 RS256(비대칭, 공개키로 검증)을 쓴다고 합시다. 공격자가 `alg`를 HS256(대칭, 같은 키로 서명·검증)으로 바꾸고, 누구나 아는 공개키를 HMAC 비밀키로 사용해 서명합니다. 검증 코드가 alg를 따라 HS256으로 검증하면서 그 공개키를 키로 쓰면, 위조 서명이 유효로 판정됩니다.

## 방어: 알고리즘을 서버가 고정한다

```javascript
// 위험: 토큰이 밝힌 alg를 그대로 신뢰
jwt.verify(token, key);

// 안전: 허용 알고리즘을 서버가 화이트리스트로 못박는다
jwt.verify(token, publicKey, {
  algorithms: ["RS256"],     // 이 외의 alg는 전부 거부 (none, HS256 포함)
});
```

핵심은 `algorithms` 옵션으로 허용 알고리즘을 명시하는 겁니다. 그러면 `none`이든 `HS256`이든 서버가 기대하지 않은 알고리즘의 토큰은 전부 거부됩니다. 그리고 RS256을 쓴다면 반드시 공개키로만 검증하고, 대칭키 검증 경로가 코드에 섞이지 않게 합니다. 라이브러리는 관리되는 최신 버전을 쓰고(과거 이런 취약점들이 라이브러리 레벨에서 많이 패치됐습니다), exp·aud·iss 같은 표준 클레임 검증도 함께 켭니다.

## 정리

- JWT의 alg는 "신뢰할 입력"이 아니다. 공격자가 통제할 수 있는 값이다.
- verify에 algorithms 화이트리스트를 고정해 none·혼동 공격을 원천 차단한다.
- 비대칭 검증은 공개키 전용 경로로만, 클레임 검증까지 세트로 켠다.
