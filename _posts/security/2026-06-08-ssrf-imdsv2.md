SSRF(Server-Side Request Forgery)가 클라우드 자격증명 탈취로 이어지는 고전 경로를 공부했습니다. EC2 메타데이터 서비스가 표적입니다.

## SSRF + 메타데이터의 조합

SSRF는 서버가 외부 입력으로 받은 URL을 검증 없이 요청하게 만드는 취약점입니다. 이미지 URL을 받아 썸네일을 만드는 기능, 웹훅 URL, URL 미리보기 등이 흔한 진입점입니다. 공격자가 이 기능에 내부 주소를 넣으면 서버가 대신 그곳에 요청합니다.

클라우드에서 가장 위험한 표적은 메타데이터 서비스 주소 `169.254.169.254`입니다. EC2 인스턴스는 여기서 자신에게 부여된 IAM 역할의 임시 자격증명을 받습니다. SSRF로 이 주소를 부르면:

```
http://169.254.169.254/latest/meta-data/iam/security-credentials/role-name
→ AccessKeyId, SecretAccessKey, Token 이 응답으로 노출
```

IMDSv1은 토큰 없는 단순 GET이라 SSRF 한 방이면 자격증명이 그대로 새어 나갑니다.

## 방어: IMDSv2 강제

IMDSv2는 요청 전에 PUT으로 세션 토큰을 먼저 받아야 하고, 그 토큰을 헤더에 실어야 합니다. SSRF는 대개 단순 GET만 유발할 수 있어 이 절차를 밟지 못합니다.

```bash
# 인스턴스 메타데이터 옵션: IMDSv2 필수화
aws ec2 modify-instance-metadata-options \
  --instance-id i-0abc... \
  --http-tokens required \
  --http-put-response-hop-limit 1    # 컨테이너 경유 접근 차단
```

`http-tokens required`면 토큰 없는 GET은 401로 거부됩니다. `hop-limit 1`은 메타데이터 응답이 컨테이너 네트워크를 넘어가지 못하게 해, 파드에서의 접근까지 좁힙니다. 애플리케이션 레벨에서는 SSRF 자체를 막는 방어(사용자 제공 URL의 대상 IP 검증, 사설·링크로컬 대역 차단, 리다이렉트 추적 제한)를 함께 둬야 근본이 해결됩니다.

## 정리

- SSRF의 클라우드 최악 시나리오는 메타데이터 서비스를 통한 자격증명 탈취다.
- IMDSv2 강제(http-tokens required)로 토큰 없는 GET 기반 탈취를 막는다.
- IMDSv2는 완화책이고, SSRF 입력 검증(사설 대역 차단)이 근본 방어다.
