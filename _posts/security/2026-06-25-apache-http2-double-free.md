웹 서버의 HTTP/2 구현에서 발견되는 메모리 안전 취약점 유형을 공부했습니다. Apache mod_http2의 double-free 사례(CVE 지정)를 계기로, 대응 원칙을 정리합니다.

## double-free가 왜 RCE가 되나

double-free는 이미 해제된 메모리를 다시 해제하려는 버그입니다. HTTP/2는 한 연결에 여러 스트림을 다중화하는데, 스트림을 리셋·정리하는 경로에서 해제 순서가 꼬이면 같은 메모리 청크가 두 번 free될 수 있습니다. 힙 할당자의 free 리스트가 오염되면, 공격자가 이후 할당을 조작해 임의 쓰기 → 코드 실행으로 확장할 여지가 생깁니다. 미인증 원격 요청만으로 트리거된다면 위험도가 최상입니다. 단순 크래시(DoS)를 넘어 RCE 가능성이 있는 이유입니다.

## 계층 방어

```apache
# 1. 패치가 최우선 — 알려진 CVE는 버전 업으로 닫는다
#    (해당 취약점이 수정된 버전 이상으로 업그레이드)

# 2. 스트림 상한으로 공격 표면 축소
H2MaxSessionStreams 100       # 연결당 동시 스트림 제한
H2MaxWorkers 실환경에 맞게

# 3. HTTP/2가 꼭 필요 없다면 모듈 자체를 끈다
#    a2dismod http2   (불필요한 기능 = 불필요한 위험)
```

메모리 안전 취약점은 애플리케이션이 코드로 "고칠" 수 있는 게 아니라, 패치가 본질적 해결입니다. 그래서 우선순위 1번이 신속한 버전 업입니다. 그 위에 방어를 겹칩니다. 스트림 수 제한으로 공격에 필요한 조건을 어렵게 만들고, WAF로 비정상 HTTP/2 패턴을 거르고, 워커를 비root로 돌려 설령 코드 실행이 되더라도 권한을 제한합니다. 안 쓰는 모듈을 끄는 것은 가장 확실한 공격 표면 축소입니다.

## 정리

- 서버 소프트웨어의 메모리 안전 CVE는 코드가 아니라 패치로 닫는 게 원칙이다.
- 패치 + 스트림 상한 + 비root 워커 + (미사용 시)모듈 비활성화로 겹겹이 막는다.
- CVE 공지 모니터링과 신속 패치 프로세스 자체가 가장 중요한 방어 역량이다.
