nginx 같은 핵심 인프라 소프트웨어에서 미인증 원격 코드 실행 취약점이 나왔을 때의 대응을 공부했습니다. rewrite 모듈 힙 오버플로 사례를 계기로 정리합니다.

## 힙 오버플로의 위험도

힙 오버플로는 할당된 버퍼 경계를 넘어 인접 힙 영역을 덮어쓰는 버그입니다. 요청 처리 중 특정 입력이 버퍼 크기 계산을 어긋나게 만들면, 공격자가 힙의 제어 구조(함수 포인터, 할당자 메타데이터)를 조작해 워커 프로세스에서 코드를 실행할 수 있습니다. nginx처럼 인터넷에 직접 노출된 서버에서 "인증 없이, 단일 요청으로" 트리거된다면 가장 심각한 등급입니다. 공격자는 별도 발판 없이 곧바로 서버 진입점을 얻습니다.

## 대응

```nginx
# 1. 패치 — 메모리 안전 CVE의 유일한 근본 해결
#    취약점이 수정된 버전으로 즉시 업그레이드

# 2. WAF로 익스플로잇 요청 차단 (패치까지의 시간 벌기)
#    비정상적으로 긴 URI, 의심스러운 rewrite 유발 패턴 필터

# 3. 워커를 비root로 (권한 축소)
user nginx;               # 워커가 root가 아니면 RCE 피해가 제한된다

# 4. 공격 표면 최소화
#    안 쓰는 모듈 비활성화, 불필요한 rewrite 규칙 제거
```

원칙은 앞선 서버 취약점들과 같습니다. 메모리 안전 버그는 설정으로 못 고치고 패치가 답입니다. 다만 패치 배포에는 시간이 걸리므로, 그 사이를 WAF와 권한 축소로 버팁니다. 특히 비root 워커는 "뚫려도 피해를 줄이는" 마지막 방어선입니다. 컨테이너라면 read-only 파일시스템, 최소 capability, seccomp 프로파일로 폭발 반경을 더 좁힐 수 있습니다.

이런 상황에 빠르게 대응하려면 평소에 SBOM(소프트웨어 구성 목록)과 버전 인벤토리를 갖춰, "우리가 취약 버전을 쓰는지"를 즉시 판단할 수 있어야 합니다.

## 정리

- 인터넷 노출 서버의 미인증 RCE는 최우선 긴급 패치 대상이다.
- 패치가 근본, WAF는 시간 벌기, 비root 워커·격리는 피해 축소.
- 신속 대응의 전제는 평소의 버전 인벤토리(SBOM)와 패치 파이프라인이다.
