검색 품질을 올리려고 더 좋은 임베딩 모델로 바꿨는데 오히려 검색이 완전히 망가진 사례를 공부했습니다. 벡터 공간의 성질을 몰라서 생긴 사고였습니다.

## 벡터 공간은 모델마다 다른 좌표계다

임베딩 모델은 텍스트를 고차원 벡터로 바꿉니다. 중요한 건, 이 벡터가 의미하는 "좌표계"가 모델마다 완전히 다르다는 점입니다. 모델 A가 만든 벡터와 모델 B가 만든 벡터는 차원 수가 같더라도 서로 다른 공간에 있습니다. 두 벡터 간 코사인 유사도는 아무 의미가 없습니다.

문제는 여기서 생깁니다. 기존 문서는 모델 A로 색인해 둔 채 모델만 B로 바꾸면, 새 질의(B로 임베딩)와 기존 문서 벡터(A로 임베딩)를 비교하게 됩니다. 서로 다른 좌표계의 벡터를 비교하니 유사도 순위가 무작위에 가까워지고, 검색이 통째로 무너집니다. "모델만 교체"가 100% 실패하는 이유입니다.

## 전량 재색인 + 버전 태깅

원칙은 하나입니다. 임베딩 모델을 바꾸면 모든 문서를 새 모델로 다시 임베딩해야 합니다. 안전한 마이그레이션 절차는 이렇습니다.

```python
# 각 벡터에 어떤 모델로 만들었는지 버전을 태깅
doc = {
    "id": "...",
    "embedding": embed_v2(text),
    "embed_model": "text-embed-v2",   # 버전 메타데이터
}
```

- 새 인덱스(또는 새 필드)에 모델 B로 전량 재색인합니다. 기존 인덱스는 그대로 두어 서비스를 유지합니다.
- 재색인이 끝나면 질의 경로를 원자적으로 새 인덱스로 전환합니다(blue-green).
- 벡터마다 `embed_model` 태그를 붙여두면, 나중에 섞임 사고를 방지하고 점진 마이그레이션도 가능합니다.

재색인은 문서가 많으면 비용·시간이 크므로 배치로 돌리고, 질의 임베딩과 문서 임베딩이 "항상 같은 모델"이라는 불변식을 코드로 보장하는 게 핵심입니다.

## 정리

- 임베딩은 모델마다 다른 좌표계다. 신구 벡터를 섞으면 유사도가 무의미해진다.
- 모델 교체 = 전량 재색인. 예외는 없다.
- 버전 태깅 + blue-green 전환으로 무중단·무오염 마이그레이션을 만든다.
