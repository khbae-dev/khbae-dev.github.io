LLM API 비용이 예상보다 큰 원인을 뜯어봤습니다. 매 호출마다 똑같은 내용을 반복 전송하고 있었습니다.

## 매번 다시 보내는 고정 프롬프트

LLM 요청은 대개 앞부분이 고정입니다. 긴 시스템 프롬프트, 규칙 설명, few-shot 예시, 참조 문서가 모든 호출에 똑같이 붙습니다. 사용자마다 바뀌는 건 마지막 질문 몇 줄뿐인데, 매 호출에 이 고정 프리픽스(수천 토큰)를 전부 다시 전송하고, 입력 토큰으로 매번 과금됩니다. 트래픽이 많을수록 이 반복 비용이 청구서의 대부분을 차지합니다.

## 정적 프리픽스를 캐시한다

prompt caching은 반복되는 프리픽스를 서버가 캐시해 두고, 다음 호출에서 그 부분을 대폭 할인된 가격(캐시 읽기)으로 처리하는 기능입니다.

```python
# 고정 프리픽스에 캐시 지점을 표시 (Anthropic 스타일 예시)
messages=[{
    "role": "system",
    "content": [
        { "type": "text",
          "text": LONG_SYSTEM_PROMPT + REFERENCE_DOCS,
          "cache_control": {"type": "ephemeral"} },   # 여기까지 캐시
    ],
}, {
    "role": "user",
    "content": user_question,   # 가변 부분은 캐시 뒤에
}]
```

핵심 규칙은 "변하지 않는 것을 앞에, 변하는 것을 뒤에" 배치하는 겁니다. 캐시는 프리픽스가 정확히 일치할 때만 히트하므로, 사용자 질문 같은 가변 요소가 프리픽스에 섞이면 캐시가 깨집니다. 잘 배치하면 캐시된 부분의 입력 비용이 크게 내려가고(제공사에 따라 1/10 수준), 반복 문서를 많이 쓰는 RAG·에이전트에서 효과가 특히 큽니다.

캐시에는 TTL이 있어 일정 시간 미사용 시 만료되므로, 트래픽이 꾸준한 프롬프트일수록 이득이 큽니다. 첫 호출은 캐시 기록 비용이 조금 더 든다는 점도 계산에 넣습니다.

## 정리

- LLM 비용 누수의 큰 축은 매 호출 반복 전송되는 고정 프리픽스다.
- prompt caching으로 정적 부분을 캐시하면 입력 비용이 크게 줄어든다.
- "불변 프리픽스 → 가변 입력" 순서 배치가 캐시 히트의 전제 조건이다.
